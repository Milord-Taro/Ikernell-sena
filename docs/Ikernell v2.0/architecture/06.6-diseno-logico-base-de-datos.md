# Diseño Lógico de la Base de Datos

## Objetivo

Este documento define el diseño lógico definitivo de la Base de Datos V2 de IKernell antes de su implementación física en PostgreSQL.

Su propósito es establecer la estructura de cada entidad, sus atributos, relaciones, restricciones y reglas de diseño, garantizando que el Modelo Entidad-Relación, el modelo relacional, el script SQL y la implementación del backend utilicen una única fuente de verdad.

---

# Decisiones Generales

Las siguientes decisiones aplican a toda la base de datos.

## Convenciones de identificación

- Todas las entidades utilizarán una clave primaria técnica denominada `id_<entidad>`.
- Las claves primarias serán de tipo:

```sql
INTEGER GENERATED ALWAYS AS IDENTITY
```

- Cada entidad dispondrá de un código funcional visible para el usuario denominado `codigo_<entidad>`.

Ejemplos:

```
ROL-001
USR-001
PRO-001
ACT-001
ERR-001
INT-001
```

Los códigos serán:

- generados automáticamente por el sistema;
- únicos;
- inmutables;
- no reutilizables.

Cuando un registro sea eliminado lógicamente o deje de existir, su código nunca volverá a utilizarse.

---

## Convenciones de nombres

- Todas las tablas utilizarán nombres en singular.
- Se utilizará la convención **snake_case**.
- Los atributos descriptivos utilizarán nombres específicos según la entidad.

Ejemplos:

```
nombre_rol
nombre_profesion
nombre_especialidad
nombre_tipo_error
```

---

## Auditoría

Las modificaciones serán registradas mediante una entidad transversal denominada **Trazabilidad**.

Por esta razón, las entidades no almacenarán el atributo:

```
fecha_actualizacion
```

salvo que una regla de negocio futura lo requiera expresamente.

---

## Eliminación lógica

Las entidades administrables utilizarán el mecanismo de eliminación lógica definido para su naturaleza.

• Los catálogos y usuarios utilizarán el atributo activo.

• Las entidades con ciclo de vida utilizarán el atributo estado.

• Las entidades históricas conservarán su información mediante fechas y reglas de negocio.

No se eliminarán físicamente registros relacionados con información histórica.

# Entidad: Usuario

## Tipo

Entidad transaccional.

- El correo electrónico deberá ser único.
- El número de identificación deberá ser único.

- Solo podrán asignarse roles activos.
- Solo podrán asignarse profesiones activas.
- Solo podrán asignarse especialidades activas.
- No podrá inhabilitarse un usuario con actividades en estado **Pendiente** o **En desarrollo**.
- La información histórica del usuario deberá conservarse después de su inhabilitación.
- El correo electrónico será utilizado como identificador único para la autenticación del sistema.

## Observaciones de diseño

- La contraseña nunca será almacenada en texto plano.
- El código de usuario será generado automáticamente por el sistema.
- La autenticación se realizará utilizando el correo electrónico y la contraseña.
- La autorización se realizará mediante el rol asignado al usuario.
- La pertenencia a proyectos no se almacena directamente en esta entidad; se administra mediante **AsignacionProyecto**.
- La profesión y la especialidad corresponden al perfil profesional del trabajador y no a su función dentro de un proyecto.

# Entidad: AsignacionProyecto

## Tipo

Entidad de relación.

## Propósito

Administrar la participación de los trabajadores dentro de cada proyecto.

Esta entidad representa el equipo de trabajo del proyecto.

## CRUD

Sí.

Administrado por el Coordinador.

## Auditoría

Sí.

## Eliminación lógica

No.

Las relaciones conservarán historial mediante fechas.

## Relaciones

```
Usuario

1 -------- N

AsignacionProyecto

N -------- 1

Proyecto
```

## Atributos

| Campo | Tipo | NN | PK | FK | UQ | Editable |
|--------|------|:--:|:--:|:--:|:--:|:--:|
| id_asignacion_proyecto | INTEGER IDENTITY | ✓ | ✓ | | | ✗ |
| id_usuario | INTEGER | ✓ | | ✓ | | ✓ |
| id_proyecto | INTEGER | ✓ | | ✓ | | ✓ |
| rol_proyecto | VARCHAR(30) | ✓ | | | | ✓ |
| fecha_asignacion | DATE | ✓ | | | | ✗ |
| fecha_desvinculacion | DATE | | | | | ✓ |

## Restricciones

- Un usuario no podrá registrarse dos veces como integrante activo del mismo proyecto.
- Solo podrán asignarse usuarios activos.
- Solo podrán asignarse proyectos activos.
- Un integrante con actividades pendientes o en desarrollo no podrá ser desvinculado.
- La desvinculación conservará el historial de participación.
- El rol del proyecto únicamente podrá ser Líder o Desarrollador.

## Restricción de unicidad

Debe existir una restricción que impida registrar más de una asignación vigente para el mismo usuario dentro del mismo proyecto. Una asignación se considerará vigente cuando la fecha_desvinculacion sea nula.

## Observaciones de diseño

- Esta entidad representa el equipo del proyecto.
- Todas las asignaciones de actividades dependerán previamente de esta relación.
- La pertenencia al proyecto será independiente del rol global del usuario.
- Un trabajador podrá pertenecer simultáneamente a varios proyectos.
- El rol dentro del proyecto podrá diferir del rol global asignado al usuario.
- Una asignación permanecerá vigente mientras la fecha_desvinculacion sea nula.

- Pendiente
- En desarrollo
- Finalizada
- Cancelada

- Cada actividad tendrá un único responsable.
- Si una tarea requiere varios desarrolladores, deberá dividirse en actividades independientes.
- RegistroError e Interrupcion dependerán directamente de la actividad.
- La trazabilidad registrará todos los cambios relevantes sobre la actividad.

# 9. Políticas de integridad referencial

La base de datos seguirá las siguientes políticas para las claves foráneas.

## ON DELETE

Como regla general se utilizará:

ON DELETE RESTRICT

para impedir la eliminación física de registros relacionados.

La conservación de la información histórica será gestionada mediante eliminación lógica.

---

## ON UPDATE

Como regla general se utilizará:

ON UPDATE CASCADE

cuando aplique sobre claves referenciadas.

---

## Excepciones

Las excepciones deberán documentarse explícitamente cuando una relación requiera un comportamiento diferente por razones de negocio.

# 10. Convenciones SQL

Las siguientes convenciones deberán aplicarse durante la implementación física de la Base de Datos V2.

---

## Nombres de tablas

- Todas las tablas utilizarán nombres en singular.
- Se empleará la convención **snake_case**.

Ejemplos:

```
usuario
proyecto
actividad
registro_error
tipo_error
mensaje_contacto
```

---

## Claves primarias

Todas las entidades utilizarán una clave primaria denominada:

```
id_<entidad>
```

Ejemplos:

```
id_usuario
id_proyecto
id_actividad
```

Las claves primarias serán de tipo:

```sql
INTEGER GENERATED ALWAYS AS IDENTITY
```

---

## Claves foráneas

Las claves foráneas utilizarán el nombre:

```
id_<entidad_referenciada>
```

Ejemplos:

```
id_usuario
id_proyecto
id_actividad
```

El tipo de dato deberá ser exactamente el mismo de la clave primaria referenciada.

---

## Códigos funcionales

Todas las entidades administrables dispondrán de un código visible para el usuario denominado:

```
codigo_<entidad>
```

Ejemplos:

```
codigo_usuario
codigo_proyecto
codigo_actividad
```

Los códigos serán:

- generados automáticamente por el sistema;
- únicos;
- inmutables;
- no reutilizables.

---

## Campos descriptivos

Los atributos descriptivos utilizarán nombres específicos según la entidad.

Ejemplos:

```
nombre_usuario
nombre_proyecto
nombre_etapa
nombre_tipo_error
```

Las descripciones utilizarán el atributo:

```
descripcion
```

Los eventos registrados utilizarán el atributo:

```
detalle
```

---

## Tipos de datos

| Tipo de información | Tipo SQL |
|----------------------|----------|
| Identificadores | INTEGER GENERATED ALWAYS AS IDENTITY |
| Códigos | VARCHAR |
| Nombres | VARCHAR |
| Correos electrónicos | VARCHAR |
| hash_contrasena | VARCHAR(255) |
| Descripciones | TEXT |
| Fechas | DATE |
| Fecha y hora | TIMESTAMP |
| Estados simples | BOOLEAN |
| Dominios controlados | VARCHAR + CHECK |

---

## Restricciones

Como regla general:

- PRIMARY KEY para toda entidad.
- FOREIGN KEY para todas las relaciones.
- UNIQUE para códigos, correos electrónicos y números de identificación.
- NOT NULL para todos los atributos obligatorios.
- CHECK para validar reglas simples de negocio.

---

## Auditoría

Las modificaciones serán registradas mediante la entidad:

```
trazabilidad
```

Por lo tanto, las entidades no almacenarán:

```
fecha_actualizacion
```

salvo que una futura necesidad del negocio lo requiera.

---

## Eliminación lógica

Las entidades administrables utilizarán el mecanismo de eliminación lógica definido para su naturaleza.

• Los catálogos y usuarios utilizarán el atributo activo.

• Las entidades con ciclo de vida utilizarán el atributo estado.

• Las entidades históricas conservarán su información mediante fechas y reglas de negocio.

La eliminación física solo será permitida cuando no afecte la integridad histórica del sistema.

---

## Principios de implementación

Durante la construcción del script SQL deberán mantenerse los siguientes principios:

- Mantener una única fuente de verdad para cada dato.
- Evitar duplicidad de información.
- Cumplir la Tercera Forma Normal (3FN).
- Priorizar la integridad referencial.
- Favorecer un modelo simple, consistente y escalable.
- Garantizar la trazabilidad de las operaciones relevantes.
- Implementar únicamente estructuras respaldadas por los requerimientos funcionales, historias de usuario y reglas de negocio.
