# Estándares de Base de Datos

## Objetivo

Este documento define las convenciones de modelado que deberán aplicarse en la base de datos de IKernell. Su propósito es garantizar consistencia, facilitar el mantenimiento, reducir la duplicidad de criterios y servir como guía para el diseño del modelo relacional, el script SQL, el diagrama entidad-relación y la implementación del backend.

---

# 1. Convenciones de nombres

## Tablas

- Todas las tablas se nombrarán en singular.
- Se utilizará el formato **snake_case**.

Ejemplos:

- usuario
- proyecto
- asignacion_proyecto
- mensaje_contacto
- tipo_error

---

## Columnas

Todas las columnas utilizarán **snake_case**.

Ejemplos:

id_usuario

fecha_inicio

fecha_fin

correo_electronico

tipo_identificacion

---

## Claves primarias

Toda entidad utilizará el prefijo:

id_

Ejemplos:

id_usuario

id_proyecto

id_actividad

id_tipo_error

---

## Códigos funcionales

Los códigos visibles para el negocio utilizarán el prefijo:

codigo_

Ejemplos:

codigo_usuario

codigo_proyecto

codigo_error

---

# 2. Tipos de datos

## Claves primarias

Las claves primarias utilizarán:

INTEGER GENERATED ALWAYS AS IDENTITY

Ejemplo

```sql
id_usuario INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

---

## Claves foráneas

Las claves foráneas utilizarán exactamente el mismo tipo de dato de la clave primaria referenciada.

Ejemplo

```sql
id_usuario INTEGER NOT NULL
```

---

## Texto corto

Para nombres, títulos y códigos:

VARCHAR

La longitud dependerá del atributo.

---

## Texto largo

Para observaciones, descripciones o comentarios:

TEXT

---

## Fechas

Solo fecha:

DATE

Fecha y hora:

TIMESTAMP

---

## Valores lógicos

Cuando únicamente existan dos estados posibles se utilizará:

BOOLEAN

Ejemplo

activo BOOLEAN NOT NULL DEFAULT TRUE

---

## Estados de negocio

Cuando existan múltiples estados se utilizará:

VARCHAR

acompañado de restricciones CHECK.

Ejemplo

estado VARCHAR(30)

---

# 3. Restricciones

## NOT NULL

Todos los atributos serán obligatorios por defecto.

Solo se permitirá NULL cuando el negocio lo justifique explícitamente.

---

## UNIQUE

Se utilizará en:

- códigos
- correo electrónico
- número de identificación

cuando corresponda.

---

## CHECK

Se utilizarán restricciones CHECK para validar reglas simples de negocio.

Ejemplos:

- fecha_fin >= fecha_inicio
- duracion_minutos > 0
- estados permitidos

---

## FOREIGN KEY

Todas las relaciones obligatorias deberán implementarse mediante claves foráneas.

---

# 4. Convenciones de fechas

Las fechas se clasifican según su propósito.

## Auditoría

Permiten conocer cuándo fue creado o actualizado un registro.

Ejemplos:

fecha_creacion

fecha_actualizacion

---

## Vigencia

Representan el período de ejecución de una entidad.

Ejemplos:

fecha_inicio

fecha_fin

---

## Eventos

Representan momentos específicos del negocio.

Ejemplos:

fecha_registro

fecha_atencion

fecha_cierre

fecha_lectura

---

## Relaciones

Representan el ciclo de vida de una relación entre entidades.

Ejemplos:

fecha_asignacion

fecha_desvinculacion

---

# 5. Estados

## Catálogos

Los catálogos utilizarán:

activo BOOLEAN

No se eliminarán físicamente.

---

## Entidades de negocio

Las entidades con múltiples estados utilizarán un atributo:

estado

acompañado por restricciones CHECK y reglas de negocio.

---

# 6. Eliminación lógica

El sistema priorizará la conservación de la información histórica.

Las entidades administrables utilizarán inhabilitación lógica cuando el negocio lo requiera.

No se eliminarán registros con información relacionada.

---

# 7. Auditoría

La trazabilidad será implementada mediante una entidad transversal de auditoría.

No se crearán tablas independientes de historial para cada entidad salvo que el negocio lo requiera explícitamente.

---

# 8. Normalización

El modelo relacional deberá cumplir, como mínimo, con la Tercera Forma Normal (3FN).

Se evitará:

- duplicidad de información
- dependencias transitivas
- atributos calculables almacenados
- relaciones redundantes

---

# 9. Integridad referencial

Las relaciones deberán preservar la integridad de la información.

Se priorizará el uso de restricciones que impidan eliminar información relacionada, favoreciendo la inhabilitación lógica sobre la eliminación física.

---

# 10. Principios de diseño

Durante la evolución de la base de datos se aplicarán los siguientes principios:

- Mantener una única fuente de verdad para cada dato.
- Evitar duplicidad de información.
- Modelar entidades según el dominio del negocio.
- Favorecer la reutilización de catálogos.
- Mantener un modelo simple, consistente y escalable.
- Priorizar la claridad del modelo sobre la complejidad innecesaria.

Toda nueva entidad o atributo deberá responder a un requerimiento funcional, una historia de usuario o una regla de negocio previamente documentada. No se incorporarán estructuras al modelo de datos únicamente por anticipar necesidades futuras.
